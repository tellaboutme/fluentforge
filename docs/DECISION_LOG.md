# Decision Log

Record significant product and architecture decisions here or add an ADR under `docs/decisions/`.

| Date | Decision | Reason | Status |
|---|---|---|---|
| 2026-07-26 | Track skill dimensions independently | A single level hides important asymmetry | Accepted |
| 2026-07-26 | Keep AI optional | Core learning must remain self-hostable and usable without paid inference | Accepted |
| 2026-07-26 | Preserve raw evidence | Mastery models and evaluators will evolve | Accepted |
| 2026-07-26 | Use versioned curriculum and prompts | Reproducible scoring and safe iteration | Accepted |
| 2026-07-26 | SQLite for development, PostgreSQL for production | A clean clone must run with no Docker and no services. Portable column types (`GUID`, `JSONB`, `UTCDateTime`) keep one model set valid on both; CI proves the migrations on PostgreSQL. | Accepted |
| 2026-07-26 | Support Python 3.10+ rather than 3.12 only | Nothing in the codebase needs 3.11/3.12 syntax. A lower floor widens where the project can be self-hosted and verified. `StrEnum` is a local `str, Enum` subclass and `UTC` is `timezone.utc`. | Accepted |
| 2026-07-26 | bcrypt + PyJWT directly, no auth framework | Small dependency surface, obvious failure modes, no vendor lock-in for a self-hostable product. Passwords are policy-checked before hashing so a weak password never creates a row. | Accepted |
| 2026-07-26 | Published curriculum versions are immutable | Evidence is scored against a specific version. Editing published source is rejected by hash comparison; authors bump `framework.yml: version` instead. | Accepted |
| 2026-07-26 | `cefr_estimate` is null until a skill reaches `supported` | Showing an unassessed skill as "A1" invents a measurement. The UI must render "needs evidence" instead. | Accepted |
| 2026-07-26 | Mastery thresholds are snapshotted onto the curriculum version | Changing a threshold later must not silently reinterpret evidence already collected. | Accepted |
| 2026-07-26 | Prerequisite edges are derived across adjacent CEFR levels within a domain | A documented default, not a claim about acquisition order. Hand-authored edges land with Milestone 6. | Provisional |
| 2026-07-26 | Skill nodes are 1:1 with curriculum objectives | The current source has one can-do per competency per level. Revisit when objectives gain sub-skills. | Provisional |
| 2026-07-26 | Mastery uses a Beta-Bernoulli posterior, not Elo | The posterior carries its own evidence mass, which is exactly what `confidence` needs, and every intermediate number stays inspectable. Each observation contributes a fractional pseudo-count, never a whole one. | Accepted |
| 2026-07-26 | Evidence weight is a product of six bounded factors | Evidence type, independence, novelty, difficulty relevance, evaluator confidence, and repetition damping. Multiplying independently testable factors keeps the model explainable; one opaque score would not be. | Accepted |
| 2026-07-26 | `skill_states` is a derived cache, recomputed from full evidence history | Nothing may write mastery directly. Replaying raw `evidence_events` means the model can be replaced without invalidating history. Incremental updates are an optimisation for later. | Accepted |
| 2026-07-26 | Confidence decays with time; mastery probability does not | Not practising makes us less certain, not the learner less able. Halves every 30 days by default. | Accepted |
| 2026-07-26 | Diagnostic item selection is a staircase, not IRT | With ~30 items an latent-trait calibration would be false precision. Failure lowers the estimate further than success raises it, because stranding a learner on inaccessible items is the worse error. | Accepted |
| 2026-07-26 | The diagnostic reports a `starting_band` separate from mastery | A 20-item diagnostic cannot support a can-do claim, so every skill stays `emerging`. The product still needs to know where to open. The band is explicitly a routing decision, not a placement, and is labelled as such in the report caveats. | Accepted |
| 2026-07-26 | Item bank is versioned inside `curriculum/` | Items are curriculum content and must be validated against the same skill keys. Bumped the curriculum to 0.2.0. Will move to the `activities` table in Milestone 3 once the bank outgrows a single file. | Provisional |
| 2026-07-26 | Refuse to start in production/staging with development defaults | Convenience defaults are what make a clean clone work and also what ships by accident. Failing loudly at startup beats issuing forgeable tokens. | Accepted |
| 2026-07-26 | The web app owns snake_case→camelCase translation in one place | `lib/api.ts` is the only module that sees a wire shape. Components consume the same camelCase types as `packages/contracts`. | Accepted |
| 2026-07-26 | Contract tests run against captured real API payloads | A hand-written typed client encodes an *assumption* about the API. `apps/web/fixtures/api-payloads.json` is captured from the running app by `make capture-fixtures`, and CI fails if it drifts. This catches renamed or dropped fields, which types alone cannot. | Accepted |
| 2026-07-26 | Access token in `sessionStorage`, read via `useSyncExternalStore` | A refresh keeps the session; closing the browser ends it. Interim: an httpOnly SameSite cookie is stronger but needs cookie support the API does not have yet. Revisit with deployment hardening. | Provisional |
| 2026-07-26 | The UI renders `—` and "needs evidence", never a level the API withheld | The API withholds `cefr_estimate` until evidence supports it; a client that substituted a plausible level would defeat the whole model. Enforced by tests in `lib/labels.test.ts` and `lib/contract.test.ts`. | Accepted |
| 2026-07-26 | Confidence is shown in words, not percentages | "Moderate confidence" is honest about a Beta posterior; "62%" implies precision the model does not have. | Accepted |
| 2026-07-26 | Pin exact web dependency versions, no carets | The repo previously used `latest` everywhere, so no two installs matched. Exact pins plus a committed `pnpm-lock.yaml` make builds reproducible. | Accepted |
| 2026-07-26 | Two layers of UI testing: jsdom components and Playwright browser | Component tests drive real components through accessible names and keystrokes and run in milliseconds on every commit; Playwright covers what jsdom cannot model (focus order across navigation, real layout, two live servers). Neither replaces the other. | Accepted |
| 2026-07-26 | UI tests assert on roles and accessible names, never on CSS classes | A test that queries `.skill-card strong` passes while a screen reader gets nothing. Querying the way assistive technology does makes accessibility a build failure rather than an audit item. | Accepted |
| 2026-07-26 | Playwright starts both servers itself against a throwaway database | `scripts/e2e-api.sh` migrates, seeds, and serves on a dedicated port, so `make e2e` needs no manual setup and cannot damage working data. | Accepted |
| 2026-07-26 | Written responses are scored by countable checks only, and marked provisional | Length, sentences, connectives and required content are measurable without a model; accuracy, precision and register are not. The honesty is numeric, not just documentary: written evidence carries `evaluator_confidence = 0.45`, so it moves mastery less than a rubric-scored result would. | Accepted |
| 2026-07-26 | A written response scores the *proportion* of checks met | All-or-nothing would record a long, on-topic, under-linked answer as zero evidence, which is false. Partial credit reflects partial evidence. | Accepted |
| 2026-07-26 | Writing does not move the difficulty staircase | The staircase is built from right/wrong closed items. A writing score is not a correctness signal, so feeding it in would corrupt the estimate — the same reason self-ratings are excluded. | Accepted |
| 2026-07-26 | The writing task is held back until ~8 closed items are answered | The prompt should match a settled ability estimate rather than the starting guess. It is still offered after three consecutive failures: production is the strongest evidence available, and a struggling learner should not be denied the chance to show it. | Accepted |
| 2026-07-26 | Provider layer added with only `disabled` implemented | Unimplemented modes raise at startup instead of silently degrading. Every test runs against `disabled`, so "AI is optional" is continuously verified rather than asserted. | Accepted |
| 2026-07-26 | AI evaluations must cite evidence and clear a confidence bar | `WritingEvaluation.is_usable` requires non-abstention and confidence ≥ 0.6 before any evidence is recorded, and priority feedback is capped at three items. Enforced by the schema, not by convention. | Accepted |
| 2026-07-27 | Plan priority is a sum of named components, never one score | `docs/ADAPTIVE_ENGINE.md` forbids an opaque magic number. Ten bounded components are computed separately and *all* of them are persisted on the plan item — including those that scored zero, because "why not something else?" needs them too. | Accepted |
| 2026-07-27 | Scoring and selection are separate stages | Ranking alone would fill a session with six grammar drills. A session template, a minute budget, a receptive/productive balance, and a cap on consecutive heavy work are applied *after* scoring. Those constraints are what make the output a plan. | Accepted |
| 2026-07-27 | Expected learning gain peaks at moderate mastery and requires evidence | `docs/LEARNING_SCIENCE.md`: comfortable is not well calibrated, and neither is hopeless. Without evidence the mastery estimate is a placeholder, so the component scores zero rather than ranking a guess. | Accepted |
| 2026-07-27 | A measured-but-weak skill outranks a never-assessed one | Unmeasured is not the same as known-to-be-weak. Before this distinction existed every plan item scored identically and the plan did not react to the diagnostic at all. | Accepted |
| 2026-07-27 | Unmet plan constraints are reported, not hidden | A plan missing a productive task says so. Silently returning four items would make a thin plan look like a complete one. | Accepted |
| 2026-07-27 | Today's plan is generated once and then stable | `GET /plans/today` is idempotent per day. A plan that reshuffles on every page load cannot be trusted or followed; regeneration is an explicit request. | Accepted |
| 2026-07-27 | Review scheduling uses stability + difficulty, deterministically | A transparent two-parameter model in the family of modern SRS. `docs/ADAPTIVE_ENGINE.md` permits it and warns against claiming memory prediction — so the module only turns an outcome into an interval, with no randomness, making it fully testable. | Accepted |
| 2026-07-27 | Each retrieval mode is scheduled separately, with its own interval factor | Recognising a word, recalling it, and producing it are different memories. Production modes get shorter intervals because they decay faster. Passing a recognition review says nothing about availability for speech. | Accepted |
| 2026-07-27 | A review mode maps to a fixed evidence type | A recognition review can never be recorded as production evidence, whatever the learner got right. Enforced by a lookup table, not by the caller. | Accepted |
| 2026-07-27 | Four grades, self-reported, rather than right/wrong | "Wrong" and "right but slow" deserve different intervals, and the learner is the only one who knows which it was. Collapsing them discards the most useful signal. | Accepted |
| 2026-07-27 | A lapse resets stability to a floor, not to zero | Relearning is faster than learning; scheduling a lapsed card as though it were brand new wastes the learner's time. | Accepted |
| 2026-07-27 | The due queue is capped | `docs/ADAPTIVE_ENGINE.md` asks for a *manageable portion* of due reviews. Presenting a 300-card backlog is how people quit. | Accepted |
| 2026-07-27 | A due card never ships its own answer | The API returns `meaning` and `example` as null until the learner has graded themselves. A card containing its answer is not a retrieval test, and retrieval is the entire mechanism. | Accepted |
| 2026-07-27 | The lexical bank is phrase-first | "make a decision" is worth more than "decision": collocations are where errors live (`docs/SKILL_MATRIX.md` §8). Validation rejects an example that does not actually use the item. | Accepted |
| 2026-07-27 | Completing the diagnostic seeds the review deck | The diagnostic has just established roughly where the learner is, which is exactly what scopes a useful starting deck. Seeding one level above the band, so review reaches slightly beyond comfort. | Accepted |
| 2026-07-27 | The test suite runs in parallel by default | Tests are independent (each gets its own in-memory database). At 261 tests a serial run had grown past a usable feedback loop. | Accepted |
| 2026-07-27 | Activities are derived from versioned source, not stored as rows | The reading library lives in `curriculum/content/` and is validated with everything else, so activities stay immutable and reviewable. A persisted `activities` table arrives when generation and imports do. | Provisional |
| 2026-07-27 | The text stays on screen while comprehension questions are answered | Hiding it would silently turn a reading task into a memory test, measuring something the profile does not claim to track. | Accepted |
| 2026-07-27 | Reading records `comprehension`, never production evidence | Understanding a text is not the same as being able to produce language, however well the learner scores. | Accepted |
| 2026-07-27 | Each text is its own evidence context | Reading three different texts is broader evidence than answering three questions about one, and the mastery model's breadth requirement should reflect that. | Accepted |
| 2026-07-27 | Plan selection breaks ties towards openable activities | Given two equally valuable candidates, offer the one a learner can actually start. Before this rule the plan preferred abstract skill placeholders and nothing could be opened. | Accepted |
| 2026-07-27 | A plan item that cannot be opened is not linked | A link that goes nowhere is worse than plain text. Kinds without activities render unlinked until they exist. | Accepted |
| 2026-07-27 | An error must recur before it is scheduled | A one-off slip is noise; practising it wastes the learner's time. Errors that block meaning skip the threshold, following the ranking in `docs/LEARNING_SCIENCE.md`. | Accepted |
| 2026-07-27 | Error cards ask for production, not recognition | An error is fixed when the learner produces the correct form themselves, not when they spot it in a list. | Accepted |
| 2026-07-27 | A resolved error keeps its record but stops being scheduled | Progress in this product is *fewer repeated errors*, so a resolved pattern is a result worth keeping, not a row to delete. | Accepted |
| 2026-07-27 | Errors name a linguistic *feature*, not the skill an item belonged to | `item.<skill_key>` filed "confuses since/for" and "cannot form a question" identically, so none of the three priorities in `docs/LEARNING_SCIENCE.md` — blocks meaning, repeats, matches the objective — was decidable. A closed taxonomy of ~36 features (`apps/api/app/learning/taxonomy.py`) makes "the same error" mean something. | Accepted |
| 2026-07-27 | The feature taxonomy is closed, and unknown codes fail validation | A typo in curriculum source would otherwise create a category nothing can practise. Content naming an unknown feature is a build failure. The set is deliberately coarse: thirty features an author can hold in their head beat two hundred nobody selects correctly. | Accepted |
| 2026-07-27 | `typically_blocks_meaning` is a default, not a verdict | Whether a slip actually cost the reader the message depends on the utterance, so content and evaluators may override it per occurrence. | Accepted |
| 2026-07-27 | Legacy `item.<skill>` error codes are kept readable, not migrated or deleted | They are real history. `label_for` renders them, and they are excluded from feature-based remedies because no study unit can honestly claim to fix an error that names no feature. | Accepted |
| 2026-07-27 | Study units record `controlled_recall` at reduced independence | The explanation stays on screen while the learner practises — that is what a study unit is. `docs/LEARNING_SCIENCE.md` is explicit that a correct answer with the rule in front of you is weaker evidence than unaided recall, so independence is 0.65 and hints lower it further. The UI says so too. | Accepted |
| 2026-07-27 | Hints are self-reported and reduce weight rather than invalidating evidence | The client counts revealed explanations. Trusting it is a real limitation; the worst a miscount can do is mis-weight one observation, which is a better failure than refusing to record scaffolded practice at all. | Accepted |
| 2026-07-27 | A study unit is one evidence context, whatever its item count | Answering five items about one point is one context. Counting per item would let a single sitting satisfy the mastery model's breadth requirement on its own. | Accepted |
| 2026-07-27 | Wrong items are logged once per feature, not once per item | Two slips on the past simple in one sitting are one observation of that weakness. Per-item counting would let a single unit push a feature past the recurrence threshold — the "recent repeated attempts cannot prove generalised mastery" invariant, read backwards. | Accepted |
| 2026-07-27 | A recurring error opens the study unit that drills its feature | An error log that only accumulates is a list of grievances. Where a unit covers the named feature, the plan item points at it; where none does, the candidate stays honestly unopenable. | Accepted |
| 2026-07-27 | A writing response too short to judge records no evidence, not a bad score | "Not enough to say" and "said badly" are different claims. The attempt is still kept: it is history even when it evidences nothing. | Accepted |
| 2026-07-27 | Writing evidence carries full independence and reduced evaluator confidence | The learner composed the text unaided — that part is not in doubt. The uncertainty is entirely in the grading, so it belongs in `confidence` (0.45), not in `independence`. Conflating the two would misreport what happened. | Accepted |
| 2026-07-27 | A writing task may not require wording its prompt never uses | Required elements are matched as literal substrings, so a task asking the learner to "apologise" while checking for "sorry" marks them down for a word nobody asked for. The parser rejects it, making the trap impossible rather than merely discouraged. | Accepted |
| 2026-07-27 | Each session slot is filled only from its own source | A `study` slot is never filled with a reading text, even when one exists for the skill. Substituting input for study would quietly dismantle the receptive/productive balance the template exists to enforce. | Accepted |
| 2026-07-27 | Activities are a discriminated union on `activity_type`, not one shape with optional fields | A reading task has no word limit and a writing task has no options. A type admitting both lets a client render nonsense; the union makes exhaustive handling a compile error in the web app. | Accepted |
| 2026-07-27 | Fixture capture disposes its engine before deleting its scratch database | SQLAlchemy pools connections, so the SQLite file stayed open. POSIX unlinks open files happily; Windows refuses, which turned tidying up into a crash *after* every payload had been captured — losing the whole run. `ignore_cleanup_errors` is kept as a backstop so the worst case is a leaked temp file, not a lost run. | Accepted |
| 2026-07-27 | Listening ships transcripts, not audio, and the client speaks them | Recordings are large, carry licensing questions the rest of the curriculum avoids, and generating them needs a paid service `docs/PRODUCT_SPEC.md` says the core loop must work without. Browser speech synthesis costs nothing, works offline, and needs no key. `audio` exists on every clip so a deployment can point at real recordings with no schema change. | Provisional |
| 2026-07-27 | Synthesised listening evidence is flagged as such | Synthetic speech under-represents weak forms, elision and assimilation — the things that actually make listening hard. `synthesised: true` on the evidence means a later audit can tell which measurements were gathered this way rather than discovering it by surprise. | Accepted |
| 2026-07-27 | The transcript is hidden by the UI, not withheld by the API | It is the stimulus, not an answer key: the client has to speak it, and a learner who cannot use audio has no other route through the exercise. Withholding it would make the lab inaccessible, which is not a trade this project makes. | Accepted |
| 2026-07-27 | Reading the transcript records no listening evidence at all | Reading a transcript is legitimate and sometimes necessary, but it does not demonstrate understanding by ear. The attempt is kept, the score is still shown, and the learner is told plainly why it did not count — the same shape as a writing response too short to judge. | Accepted |
| 2026-07-27 | Replays cost independence only past a free allowance | Replaying is normal listening behaviour, not cheating, so the first two passes are free and the value never falls below a floor. What it does capture is that catching a clip in two passes is stronger evidence than needing six. | Accepted |
| 2026-07-27 | Comprehension questions are defined once and shared | A gist question about a text and a gist question about a recording are the same object asking the same thing about a different stimulus. One definition in `curriculum/questions.py` means the reading and listening labs cannot drift apart in what they validate or withhold. | Accepted |
| 2026-07-27 | The captured API fixture is stabilised, not raw | CI proves the committed fixture is current by re-capturing and diffing, which requires byte-identical output for the same API. Generated UUIDs, timestamps and dates are replaced with placeholders that preserve shape *and identity* — fields sharing a real identifier still share a placeholder, so a client asserting two fields agree keeps working. Without this the `fixtures` job could never have passed, and it did not on the first push. | Accepted |
| 2026-07-27 | Line endings are normalised to LF by `.gitattributes` | Development is on Windows, CI on Linux. Python's text mode writes CRLF on Windows, so a file regenerated on Linux differed on every line. The capture script now pins `newline="\n"` and git stores LF, fixing both the generation and the storage side. | Accepted |
| 2026-07-27 | A rubric judgement adds a second evidence event, never replacing the deterministic one | They make different claims — that language was produced, and how good it was. Overwriting would discard the first, and a later change of evaluator would silently rewrite history. Both share a context key so one piece of writing judged twice stays one context. | Accepted |
| 2026-07-27 | Evaluator confidence is capped at 0.85 before reaching the mastery model | A model reporting 0.95 has not earned the trust of a closed item scored against a known answer. `docs/AI_TUTOR_BEHAVIOR.md` makes AI judgement an accelerator, not an authority, and the cap is where that becomes arithmetic rather than sentiment. | Accepted |
| 2026-07-27 | The evaluator call is total, and a short response never reaches it | A provider is third-party code reached over a network; the protocol says it returns `None` rather than raising, but that is enforced at the call site rather than trusted. A learner's submission must never be lost to somebody else's exception. Responses below the length minimum are not sent at all: there is nothing to judge and no reason to spend the call. | Accepted |
| 2026-07-27 | Rubric dimensions must carry quotations, and the UI shows them | A score with no evidence is a guess. Showing what a judgement rested on is what lets a learner disagree with it rather than simply receive it. | Accepted |
| 2026-07-27 | The E2E API launcher is Python, not bash | `bash` on a Windows dev machine resolves to WSL, and a broken WSL failed the whole suite before one test ran. Python is already a hard requirement on every platform this runs on, so the launcher now has no dependency the project does not. | Accepted |
| 2026-07-27 | The app marks the document `data-hydrated` when React takes over | A controlled input silently discards keystrokes that arrive before hydration. Invisible to humans, it made the keyboard-only journey submit an empty name. The marker gives tests — and anything else fast — a deterministic signal instead of a race. | Accepted |
| 2026-07-27 | E2E interactions are short-fused with report-detection as recovery | Every diagnostic transition races the UI, and the final submission replaces the form with the report mid-action. A 5s action timeout plus 'did the report appear?' on failure beats retrying a detached control for 30 seconds. | Accepted |
| 2026-07-27 | The cloud evaluator verifies that cited quotations exist in the learner's text | Schema-valid is not the same as honest. A model that fabricates evidence is not judging *this* piece of writing, and `docs/AI_TUTOR_BEHAVIOR.md` does not let that reach the mastery model. Compared on collapsed whitespace and folded case, so reflowing a line is not mistaken for invention. | Accepted |
| 2026-07-27 | The cloud evaluator is constructed even with no API key | It abstains on its own. Failing at startup would take the whole API down over a setting that only affects one optional feature; degrading to deterministic feedback is what `docs/PRODUCT_SPEC.md` asks for. | Accepted |
| 2026-07-27 | JSON is extracted by a balanced-brace scan, not a regex | Models wrap their JSON in prose or fences, so the parser is forgiving about *where* the object is. A brace inside a learner's own quoted text would defeat a regex, so the scan tracks string state and escapes. Unforgiving about content: a body failing the schema is discarded without negotiation. | Accepted |
| 2026-07-27 | The evaluator prompt is read from `prompts/` with its version | `CLAUDE.md` treats prompts as versioned product logic. The declared version travels onto every evidence event, so changing the prompt is visible in history rather than silently reinterpreting past judgements. | Accepted |
| 2026-07-27 | Prettier gets its own ignore file | It does not read `.gitignore`, so the format step was walking thousands of generated `.next/` chunks. The captured API fixture is excluded too: CI diffs it byte-for-byte, and a formatter rewriting it would break that comparison. | Accepted |
| 2026-07-27 | No speaking task may target a pronunciation skill, and the parser refuses one that does | A transcript is normalised text: it cannot tell a clearly spoken word from a badly spoken one the recogniser guessed correctly. Enforcing this in the parser rather than in review means the rule cannot be broken by content alone, and every evidence event says `pronunciation_unassessed: true` so no later reader assumes otherwise. | Accepted |
| 2026-07-27 | Recognition confidence is stored and never scored | Browser speech recognition is measurably worse on accented and non-native speech — this product's entire audience. A low-confidence transcript may mean unclear speech, a poor microphone, or a recogniser trained mostly on native speakers, and the system cannot tell which. Scoring it would be discrimination dressed as assessment. It is kept so an audit can ask whether recognition quality correlated with outcomes. | Accepted |
| 2026-07-27 | Typing instead of speaking records no speaking evidence | The mirror of reading a listening transcript. The fallback is always available, because a learner without a microphone must still be able to finish; what keeps the profile honest is that the client reports it and the API declines to record. The attempt is kept and the learner is told why it did not count, without any implication of cheating. | Accepted |
| 2026-07-27 | A transcript is weaker evidence than typed writing (confidence 0.35 against 0.45) | Both are the learner's own composition, so independence is full in each. The extra uncertainty is entirely in the record: speech recognition drops words, merges them, and silently corrects grammar. That belongs in evaluator confidence rather than anywhere else. | Accepted |
| 2026-07-27 | Speaking tasks have no upper word bound and no sentence minimum | Sentence boundaries in a transcript are a punctuation guess made by the recogniser, not something the learner produced, so requiring them would score the software. A fluent learner talking freely past the length target is the goal, not a fault. | Accepted |
| 2026-07-27 | Every speaking task states its preparation time in the curriculum | Planning time changes what a speaking task measures — spontaneous production and prepared production are different skills. Leaving it to the UI would let a styling change quietly alter the construct being assessed. | Accepted |
| 2026-07-27 | The skill graph is authored, not derived | Derivation produced one true claim — level N depends on level N-1 in the same domain — repeated 45 times. It could not express that vocabulary gates production, that interaction is listening and speaking at once, or that pronunciation gates nothing. `curriculum/graph.yml` states each claim once, with a reason, and the loader refuses to run without it: silently continuing with no dependency information would hide the gap rather than report it. | Accepted |
| 2026-07-27 | Every edge must state why it exists, in at least a sentence | An edge nobody can justify in a sentence is a guess with a weight attached. Enforced by the parser rather than by review, because the cost of an unjustified edge is paid quietly in every plan afterwards. The reason is not persisted: it belongs to the versioned, hashed source, and a database column holding a paragraph nobody queries is a worse home for it. | Accepted |
| 2026-07-27 | `supports` is a real relation, and never gates | The temptation with a graph like this is to inflate every true relationship into a prerequisite. Pronunciation genuinely helps spoken production and must not block it; grammar genuinely helps speech and must not block it. Giving those claims somewhere honest to go is what stops them becoming barriers. `downstream_reach` walks prerequisites only. | Accepted |
| 2026-07-27 | Weight means confidence in the claim, not importance of the skill | Two different things that a single number would conflate. Weights multiply along a path, so a chain of tentative claims counts for less than a chain of definitional ones — which is the behaviour wanted when reasoning about how far a weakness propagates. | Accepted |
| 2026-07-27 | Pronunciation never gates anything outside its own domain | A heavily accented speaker can be entirely successful, which is why the CEFR scales phonological control separately from spoken production. Making intelligibility a prerequisite would encode an accent standard this product does not hold, and would keep exactly the learners it serves from practising. Tested, not merely intended. | Accepted |
| 2026-07-27 | Grammar gates writing but only supports speaking | Writing is where grammatical control is both visible and expected; readers have no intonation to disambiguate with. Speech tolerates approximation, and gating spoken practice on grammar would keep a learner silent for no gain. | Accepted |
| 2026-07-27 | Prerequisite importance is a graph walk, not `1 - difficulty` | The old proxy assumed lower level means blocks more. True within a domain, false across them, and invisible in the plan explanation: A2 vocabulary and A2 pronunciation scored identically despite gating wildly different amounts. `make test-curriculum` now prints the five most load-bearing skills every run, so a change in what the planner pushes towards appears in a diff. | Accepted |
| 2026-07-27 | The graph validator refuses six specific shapes rather than warning | Cycles, backwards prerequisites, orphans above a domain floor, unjustified edges, dead rules, duplicate triples. Every one of these failures is silent — the graph loads, the planner believes it, and the learner gets a worse plan for reasons nobody can see. A warning nobody reads is not a control. | Accepted |
| 2026-07-27 | Milestone 7 opens with multi-source mediation, not more C2 vocabulary | `docs/ROADMAP.md` warns that advanced support means advanced *work*, not harder quizzes. Mediation is the one task where that difference is unmistakable: several sources go in, one account comes out, and the learner has to notice that the sources disagree and decide what the reader needs. It was also the largest gap in the product — the mediation objectives had prerequisites pointing at them and no activity behind them. | Accepted |
| 2026-07-27 | A mediation task needs at least two sources, and the parser enforces it | One source is a summary, and the writing bank already has summaries. What makes mediation hard is reconciliation, so a single-source task would carry the mediation label without the mediation demand. | Accepted |
